On the Attendance row-menu dispatch (2026-08-11), the initial brief described Keka's row-menu structure in prose ("every row ends in a ⋯ button... four actions: Regularize, Apply On Duty, Apply Partial Day, Request Leave"). I built the full first pass from that prose alone. Mid-task the user corrected: *"only our recon via agents is not the right way — we need to combine it with actual things from Keka"* and the coordinator added real screenshots at `design/reference/keka/*.jpg` + a `README.md` explaining what to take/not take. The real images revealed structure the prose never mentioned or got subtly wrong: a three-card row (Attendance Stats · Timings · Actions) above the log, a "Logs & Requests" heading with a 24-hour-format toggle, four tabs (not just a bare register), academic-session period pills, a translated column set (`DATE · ATTENDANCE VISUAL · EFFECTIVE HOURS · BREAK TAKEN · GROSS HOURS · ARRIVAL · LOG`), and — critically — the Requests tab is split into three sections BY REQUEST TYPE, not one flat list, which contradicted my own earlier brief's phrase "Regularisation requests tab."

**Why:** a prose description is filtered through the describer's own summarization judgment before it reaches me — it drops structure the describer didn't think was worth mentioning, and can misstate details (singular vs plural, flat vs sectioned) that only the pixels settle unambiguously. This is a stronger, more general instance of [[feedback-live-reference-capture-midtask]] (which was about a mid-task *description* of a live capture still being authoritative over my draft) — this time the lesson is one level up: even the description itself is not to be trusted over the source image once the image exists in the repo.

**How to apply:** before building any UI that is explicitly benchmarked against a named competitor/reference, check whether `design/reference/` (or wherever the dispatch points) already contains captured image files for it. If so, open and look at them with the Read tool FIRST, before writing any code — do not proceed from a coordinator's or your own prior prose summary of what such an image "shows." If reference images are added mid-task after you've already built from prose, treat the images as authoritative and re-plan against them rather than patching your prose-derived structure. Read the reference README for explicit "take this / not that / translate this" guidance — it usually pre-answers what should and shouldn't carry over into the project's own design language.
