`design/hi-fi/hi-fi.jsx` and `design/design-canvas.jsx` are a browser-transpiled code-as-design canvas (Babel-standalone, `tenure` preset forces classic JSX runtime), separate from `frontend/`. Each file is one big IIFE hanging everything off `window.*` (`window.G` tokens, `window.DCArtboard`, etc.) — no import/export statements permitted anywhere, and styling is inline `style={{}}` objects only (no CSS/Tailwind classes). Design tokens come from `window.G` (`G.pine`, `G.board`, `G.marigold`, `G.chalk`, `G.success/danger/info`, etc.).

**Why:** these files run directly in the browser via Babel-standalone with no build step, so any modern JS module syntax breaks the page silently at parse time.

**How to apply:** when asked to edit `design/*.jsx`, never add imports/exports, never use CSS classes, and pull all colors/spacing from `G`. JSX fragments (`<>...</>`) are fine — the file already used them before this dispatch. There's no local Babel/babel-preset-react installed in this repo to lint-check JSX changes headlessly; verify by careful brace/paren balance review and manual read-through instead of trying to run a transpile step. `React` itself (e.g. `React.Fragment` when a keyed fragment is needed inside `.map()`) is a valid bare global identifier here too — other files in this canvas already destructure hooks off it (`const { useState } = React;`), confirming the React UMD build is loaded as `window.React` before these IIFEs run.

Also: this file is actively being iterated on across multiple dispatches (options added/removed, pages restructured) — always re-read the current file in full before trusting a coordinator's description of "what's currently there" or your own memory of a prior pass; component names and page wiring can and do change between dispatches.

There is now a second, separate entry point alongside `index.html`/`hi-fi.jsx`: `design/prototype.html` + `design/prototype.jsx`, a real navigable router (no design-canvas pan/zoom chrome) that reuses screens exposed via `window.Screens = { Login: LoginView, Dashboard: DashboardView, Employee: EmployeeView }` at the bottom of `hi-fi.jsx`. The pattern: full-size, prop-driven `*View` components (`width:100%, height:100%`, take callbacks like `onContinue`/`onNavigate`/`onSignOut`/`onViewAdmin`) live in `hi-fi.jsx` next to the thin `DCArtboard`-wrapped versions (`LoginMix`, `AB_Dashboard`, `AB_Employee`) that just wrap the View in a fixed-size box for the canvas. When asked to add more screens/routes to the prototype, keep following this split — build the reusable View in `hi-fi.jsx`, wrap it for the canvas, and export it via `window.Screens` — rather than duplicating markup into `prototype.jsx`. `prototype.html`'s `<head>` intentionally mirrors `index.html`'s exactly (same CDN script tags, no SRI/integrity hashes) per direct instruction — a security-guidance hook will flag this on every Write; that's expected and consistent with the existing committed `index.html`, not an oversight to fix unilaterally.

Product-priority note: the employee self-service (ESS) surface (`EmployeeView`) was built as the *primary* surface — most Tenure users are teachers/staff, not HR admins — so the prototype's post-login default route is the employee home, not the HR `Dashboard`. The HR console is reached from the employee Profile via a "View admin console" link (`onViewAdmin`), not the default landing. Keep this priority ordering in mind for future ESS work (leave/payslips/documents/profile detail screens) — those are likely the next asks, not more admin-console depth. Content sub-views that already exist as reusable `*View`s (e.g. `MyAttendanceView`) get reused inside `EmployeeView`'s route switch, not rebuilt — check for an existing extracted view before writing a new one for a nav item.
