Built 2026-08-10/11 as one of 3 PARALLEL Home-shell variants (A/B/C, different agents, shared `design/v2/tokens.jsx` (G2) + `design/v2/kit.jsx` (UI2) as read-only input) responding to: "design looks better but the colour is all over, and the sidebar isn't looking good. Keka looks good." Diagnosis: v1 STAFFROOM's `EmployeeShell` (design/v2/screens.jsx) made the CHROME colourful (terracotta gradient sidebar + topbar slab) on top of already-colourful data — colour everywhere, nothing leads the eye.

**The technique — "calm chrome, colourful data" without editing tokens/kit:**
- `G2`'s `c.shell`/`c.shell2`/`c.onShell*`/`c.shellActive` roles exist specifically for a coloured-slab shell. To go calm, simply DON'T use them for the new shell — build sidebar/topbar backgrounds from `c.surface` (white in light, warm-dark-neutral `#241A16` in dark — NOT the terracotta `c.shell` `#4A2015`) with a `1px solid c.border` hairline separator, and canvas from `c.bg` (a shade darker/warmer than surface) so white Cards visibly lift off it. This gets "deep neutral, not a colour slab" dark-mode chrome for free because `c.surface`(dark) was already token-designed independent of the shell-gradient roles.
- Active nav item = the ONLY coloured chrome element: `background: c.accentSoft` pill (use `G.r.pill` on a full-width row — at nav-row height this renders as a stadium/pill shape) + `color: c.accent` icon+label + `fontWeight: 700`. Inactive rows: `c.inkMuted`, weight 500, no background (hover = `withAlpha(c.ink, 0.05)`).
- The kit's `LangSwitcher` (window.UI2) is hardcoded for a coloured-shell background (white-pill-on-terracotta contrast: `border: rgba(255,255,255,.28)`, active bg `#FFFFFF`, inactive `c.onShellMuted`). It is unusable on a light/neutral topbar — text disappears. Built a local `LangSwitcherB` in the variant file using `c.border`/`c.accentSoft`/`c.accent`/`c.inkMuted` instead; this is expected/sanctioned ("you MAY define local layout components inside your own file") whenever a variant's chrome direction diverges from the shell-tinted assumption baked into a kit component's own inline styles.
- `ThemeToggle` and `Button variant="icon"`/`"ghost"` from the kit DID work unmodified on the light chrome (call them with no `onDark` prop) — they already read `c.border`/`c.surface`/`c.ink` generically, not shell-tinted, so no local fork was needed there. Lesson: check whether a kit component's hardcoded-look assumption is really shell-specific before forking it locally; only `LangSwitcher` needed it here, not the whole chrome-adjacent component set.
- "Let the data be a touch bolder" was implemented as literal size bumps on the shared data components — `HoursRing size={104}` (was 92), `LeaveDonut size={124}` (was 108 default), `Glyph size={42}` on the action banner (was 38) — NOT new components. The vividness read comes from the surrounding chrome going quiet, not from changing the data components' own colour intensity (which is already vivid and untouched).

Files: `design/v2/variants/home-b.jsx` (`window.HomeVariants.B`), `design/v2-b.html` (standalone entry, `tenure` classic-JSX-runtime preset copied verbatim from `design/v2.html`). Sibling variants A and C are owned by other agents in the same wave — do not assume this file's shell approach generalizes to them without checking their output first.
